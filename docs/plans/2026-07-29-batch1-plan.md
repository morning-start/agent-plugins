## Part 1: Bug 生命周期（Gap 1）

### 现状

- implement 的"快速任务模式"中有一条 Bug Fix 最小流程（第 133 行），但没有独立成模式
- Bug Fix 与 Feature TDD 共享同一套 Iron Law，但 Bug 修复的本质是「复现→诊断→修复→回归验证」，与「Red→Green→Verify」不同
- learn 只在 implement 3 次自动修复失败后触发，但**成功的 Bug 修复更有学习价值**（根因清晰、修复验证充分）
- 路由表将 "bug"/"fix"/"debug" 映射到 `moonbit-implement (debug)`，但没有模式区分

### 设计

#### A. implement 增加 Bug Fix Mode

在 implement/SKILL.md 中新增独立章节，与 Feature TDD 模式并列。

**入口判断**：当用户请求是修复现有 bug（而非新增功能）时，进入 Bug Fix Mode。

**Bug Fix Mode 流程**：

```
┌─ REPRODUCE:  写 regression test 复现 bug → moon test -f "regr_*" (预期: 失败)
├─ DIAGNOSE:   定位根因（文件/函数/错误码）
├─ FIX:        最小修复 → moon test -f "regr_*" (预期: 通过)
├─ VERIFY:     全量测试 + fmt + check → 全部通过
└─ LEARN:      自动触发 moonbit-learn，记录根因
```

**Iron Law 补充**：

```
NO BUG FIX WITHOUT REGRESSION TEST FIRST
```

不写 regression test 就修 bug？**先写测试再修。** regression test 必须：
1. 能复现 bug（修之前跑是红的）
2. 能证明修复有效（修之后跑是绿的）
3. 命名规则：`regr_{bug_id_or_desc}`，放在测试文件末尾

**停止条件**（扩展现有停止条件表）：
- Bug 无法稳定复现 → 停止，请求用户提供更多信息
- 根因跨多个模块/API → 报告影响范围，请求用户确认修复方向
- Fix 引入回归 → 回滚 fix，重新诊断

**输出 JSON 扩展**：
```json
{
  "status": "done | paused",
  "mode": "bugfix",           // 新增：feature | bugfix
  "regression_test": "regr_edge_case_42",
  "root_cause": "空指针未检查",
  "fixed_file": "src/parser.mbt",
  ...
}
```

#### B. learn 增加 Bug Fix 自动触发

learn 当前只在"3 次自动修复全部失败"后触发。修改为：

```diff
- | `moonbit-implement` 中 3 次自动修复全部失败，用户介入解决 | 自动触发 |
+ | `moonbit-implement` 中 Bug Fix 验证通过后 | 自动触发 |
+ | `moonbit-implement` 中 3 次自动修复全部失败，用户介入解决 | 自动触发 |
```

#### C. 路由表区分 Bug Fix 入口

using-moonbit-skills/SKILL.md 中：
- Trigger Matrix 第 68 行 `"debug", "fix", "error", "bug", "fail"` → `moonbit-implement` (Bug Fix Mode)
- Skill Priority 第 42 行 `当前实现失败` → `moonbit-implement` (Bug Fix Mode)
- 增加注释说明 implement 有两种模式

#### D. 管线图更新

orchestration.md 全景图 implement 框内增加模式说明：
```
│ moonbit-implement — TDD 实现 / Bug 修复          │
│ 模式: Feature TDD | Bug Fix                       │
```

## Part 2: 文档管理（Gap 2）

### 现状

- evaluate 说"生成文档"，但无具体契约
- implement 的快速任务模式有 Documentation 类型，仅有路径/命令验证
- 没有任何技能在 pub API 变更后要求更新 docstring
- 没有任何技能在重构后要求同步设计文档
- 没有任何门禁检查文档完整性

### 设计

原则：**不新增独立 skill**，通过给现有技能增加「文档同步契约」来实现。文档同步是约束而非独立流程。

#### A. implement 增加文档同步契约

在 TDD 循环的 VERIFY 步骤后、输出前，增加文档检查：

```
VERIFY 后 → 检查 pub API 变更 → 如有变更 → 更新 docstring
                                  如有 CLI 变更 → 更新 README 用法示例
```

在 implement/SKILL.md 的"各类型 TDD 策略"表中增加一列"文档要求"：

| 类型 | 项目分类 | 验证目标 | 额外验证 | 文档要求 |
|------|---------|---------|---------|---------|
| lib | library | `moon test --target native` | `moon check --target all` | pub fn 有 docstring |
| cli | main | `moon test --target native` | `moon run .` | README 用法示例与实际输出一致 |
| c-ffi | library | `moon check --target native` | — | FFI 函数有使用说明 |
| wasm | library | `moon test --target wasm` | `moon check --target wasm-gc` | WASM 导出函数有文档 |
| parser | library | `moon test --target native` | valid/invalid/edge 分类测试 | 输入格式有说明 |
| async | library | `moon test --target native` | 并发测试、超时测试 | 并发模型有说明 |

#### B. refactor + perform 增加文档同步契约

- **refactor/SKILL.md**：重构改变模块结构或 pub API 后，更新内部设计文档（如 ADR）
- **perform/SKILL.md**：优化改变配置参数或行为后，更新配置文档

在两者的"输出"或"错误恢复"中增加文档同步项。

#### C. verify 增加文档完整性检查（S6，软性）

在 verify/SKILL.md 的软性要求中增加 S6：

```
### S6. 文档完整性

| 检查项 | 合格标准 | 动作 |
|--------|---------|------|
| pub fn docstring | 每个导出的 pub fn 有 ///
comment | 报告缺失项 |
| README 示例 | README 中的 usage 测试可运行 | 报告失败 |
| CLI --help | moon run . --help 输出非空 (main) | 报告缺失 |
```

**为什么是软性（S6）而非硬性（H8）？** 文档缺失不应阻断发布，但应报告给用户决策。硬性文档门禁可能在原型阶段造成摩擦。
