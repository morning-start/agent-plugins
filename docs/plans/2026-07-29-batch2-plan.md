## Part 1: Code Review 多轮循环（Gap 3）

### 现状

- code-review 是每任务后的**单次**审查：通过就继续，不通过修改后继续
- 没有"修改后自动重新审查"的回路
- 审查发现的问题类型（Critical/Important/Minor）有分级，但修复后没有自动回到 review

### 设计

#### A. code-review/SKILL.md 增加多轮循环契约

在审查流程的输出阶段增加多轮语义：

**输出 JSON 扩展**：
```json
{
  "status": "approved | changes_needed",
  "review_round": 2,
  "previous_round_findings": 3,
  "scope": "tasks 3-5",
  "findings": { "critical": 0, "important": 1, "minor": 3 },
  "auto_fixes": 2,
  "next": "implement | verify"
}
```

新增字段：
- `review_round`：当前是第几轮审查（从 1 开始）
- `previous_round_findings`：上一轮 found 数量（用于跟踪趋势）

**审查流程增加多轮判断**：
- Critical 问题 → 标记 `changes_needed`，必须修复，修复后自动回到 code-review
- Important 问题 → 标记 `changes_needed`，建议修复，修复后自动回到 code-review
- 只有 Critical=0 且 Important=0（或用户显式接受）时才标记 `approved`
- Minor 问题不阻断，记下稍后处理

**增加"多轮循环"说明段落**：

> ### 多轮循环
>
> code-review 支持多轮审查。每轮输出 `changes_needed` 后，Agent 应回到实现任务修复问题，修复完成后自动再次触发 code-review。同一技能实例接管上下文，review_round 递增。
> ```
> Round 1: review → changes_needed → implement (fix) → review
> Round 2: review → changes_needed → implement (fix) → review
> Round 3: review → approved → verify
> ```
> 当所有 Critical 和 Important 问题被解决，或用户显式接受已知问题后，标记 `approved`。

#### B. 管线图增加 code-review 自循环

orchestration.md 和 using-moonbit-skills 的管线图中，code-review 增加自循环箭头：
```
implement → code-review ─→ implement（若未批准）→ code-review（下一轮）
                          └→ verify（若已批准）
```

## Part 2: Spike 探索路径（Gap 4）

### 现状

- implement 的 Iron Law 非常严格：NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST
- "I need to explore first" → "Fine. Throw away exploration, start with TDD."
- 没有给"先验证假设再写代码"留合法空间

### 设计

原则：**在 plan 之后、writing-plans 之前，增加可选 Spike 步骤**。Spike 不是技能，而是 plan 的一个可选后续阶段。产出物是经验（记录到 writing-plans），不是代码。

#### A. plan/SKILL.md 增加 Spike 章节

在 plan 的输出部分增加 "Spike 原型验证" 选项：

> ### Spike 原型验证
>
> 设计确定后，如果存在关键假设需要验证（API 可用性、技术可行性、性能假设、依赖评估），可以在 writing-plans 之前增加可选 Spike 阶段。
>
> **Spike 契约**：
> 1. 写最小的探索代码，只验证关键假设
> 2. 验证完成即**丢弃所有 Spike 代码**（不可进入版本控制）
> 3. 产出物是经验：记录到 writing-plans 的任务拆解中
> 4. Spike 代码不能被复用为生产代码（否则破坏 Iron Law）

#### B. writing-plans/SKILL.md 引用 Spike

在 writing-plans 中增加 Spike 产出作为任务拆解输入：

> 如果 plan 阶段执行了 Spike 原型验证，将 Spike 的经验（可行性结论、关键发现）纳入任务拆解依据。

#### C. implement/SKILL.md 的 Common Rationalizations 更新

当前第 62 行：
> "I need to explore first" → "Fine. Throw away exploration, start with TDD."

更新为引用 Spike 阶段：
> "I need to explore first" → "在 plan 阶段使用 Spike 原型验证。验证后丢弃，再进入 TDD。"

#### D. 管线图更新

orchestration.md 全景图中增加 Spike 可选步骤：
```
plan → [Spike (可选)] → writing-plans → scaffold → implement ...
```
