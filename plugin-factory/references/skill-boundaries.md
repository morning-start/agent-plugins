# 技能职责边界与协作纪律（Skill Boundaries & Cooperation Discipline）

> **固化于：2026-08-22** · 沉淀自 flowstate 插件实战优化（7 技能、规划/执行分离、
> 内部方略路由）。references 固化集的一部分。
> **规则**：生成插件的技能拆分与协作设计遵循本文 + `skills/pf-compose/SKILL.md`
> + `references/design-principles.md`（铁律 5 职责边界）；不要重复踩坑。
> 本文是**纪律清单**（怎么做不会乱），编排模式见 `references/orchestration-patterns.md`（怎么连起来）。

## 为什么存在

插件从 1~2 个技能长大到 5+ 技能时，最大的风险不是"技能写得不好"，而是**技能之间
的职责边界糊掉**：多个技能重复写同一规则、谁执行谁规划说不清、入口路由漏场景、
概念在文档/技能/README 三处漂移。以下纪律来自 flowstate 优化实战，每条都有正反例。

---

## 纪律 1：职责边界三分离

三个"谁做"必须分开，且写进各自的 Iron Law：

| 分离 | 正面 | 反面（反例） |
|------|------|-------------|
| **规划 / 执行** | `fst-change` 只规划约束（记录→分级→评估→审批→归档），`fst-iterate` 唯一执行入口（`ALL EXECUTION FLOWS THROUGH HERE`）。Hotfix 是唯一例外（先修后补单，24h 内补录） | 变更技能归档后自己写代码 / 执行技能不写 plan 直接开写 |
| **横切能力单点维护** | 工作区规则只有 `fst-workplace` 写，其他技能一行引用，不重复定义 | 每个技能各写一套"落点规则" |
| **决策 / 执行** | 方略选择由内部 `fst-mode-router` 决策，`fst-iterate` 消费交接产物执行 | 执行技能一边干活一边临时拍脑袋选方略 |

**落地方式**：每个技能 Iron Law 用 `NO X, NO Y` 句式把边界钉死；主执行技能额外
写一条 `ALL EXECUTION FLOWS THROUGH HERE` 式的独占声明；例外（如 Hotfix）显式
写出并限定时限。

## 纪律 2：内部路由技能（Internal Router）模式

当主技能内部有一块"需要按输入特征做选择"的逻辑（选方略 / 选流程 / 选模板），
且选择需要用户确认（HITL）时，抽成**内部路由技能**：

- **不作为用户场景入口**：入口路由表（using-<plugin>）中明确标注"内部技能，用户不直接触发"
- **由主技能按需调用**：主技能第 0 步调用，接收其结构化交接产物（如 JSON `ModePlan`）
- **职责闭环**：盘点输入 → 按特征选模式 → 说明理由 → 用户确认 → 输出交接产物
- **铁律**：不写代码、不建分支、不绕过主技能的 Gate（`NO REQUIREMENT INVENTORY, NO MODE; NO USER CONFIRMATION, NO EXECUTION`）
- **description**：以 "Use internally from <主技能> to …" 开头，防止被误当入口触发

**交接产物必须结构化**（JSON + schema 可校验），主技能只消费产物、不重新决策——
这是决策/执行分离的机械保证。

## 纪律 3：入口路由场景覆盖清单

入口技能（`using-<plugin>`）的场景表必须覆盖**全部用户可达场景**，缺一个就是
路由漏洞。完整清单：

| 场景 | 示例 |
|------|------|
| 新项目 / 需求模糊 | "做个 X"、"帮我想想这个项目" |
| 变更 / 缺陷 / 事故 | 口头/IM/邮件改需求、修 bug、线上事故 |
| 验收 / 上线前 | 迭代完成、变更落地、准备发布 |
| 迭代 / 回顾 / 排期 | 开始迭代、迭代回顾、下轮排期 |
| 基础能力（横切） | 工作区初始化、落点判断、配置管理 |
| **简单任务** | 一句话能说清 diff 的直接做（不进方略） |
| 拿不准 | 回退默认技能锁底线（"拿不准 → 先 <默认技能>"） |

**规则**：场景表按"场景 → 技能 → 管哪些节点"组织；路由规则与场景表双处一致；
内部技能在表中标注非入口；`拿不准`必须有显式回退项，不猜。

## 纪律 4：框架 vs 模式两层解耦

流程类插件区分两层，**各有一个权威位置，互不绑架**：

| 层 | 是什么 | 变化频率 | 位置 |
|----|--------|---------|------|
| **流程框架** | 整套流程的结构：节点、边、循环、闸门（HITL）、检查点 | 慢——符合开发哲学，不随单一问题变化 | 独立参考文档（按插件场景命名，类似 flowstate 的 flow-graph.md） |

> 说明：上表"独立参考文档"按生成插件的实际场景命名（如 flowstate 的 flow-graph.md），
> 非 plugin-factory 固有文件；框架演进走 ADR。
| **操作模式** | 解决单一问题的方法（spec / loop / graph / todo） | 快——随经验更新、可插拔 | `references/agent-modes/*.md` 或独立技能集 |

**关系**：框架定"流程怎么走"，模式定"这一步怎么做更好"；换模式不改变框架、
更新模式不推翻流程。**权威位置必须随插件分发**（references/ 或 skills/），
不放工作区模板——放模板会导致每个项目复制一份、改时漂移回不来。

## 纪律 5：概念命名一致性（防三处漂移）

同一个概念（模式、框架、术语）在**文档 / 技能 / README / 模板**四处必须同名同义：

- 模式集一旦定版（如 todo / spec / goal / graph），全仓统一引用，不再出现旧名
- 非独立概念**降级为技能内部方法**，不占模式名（如"先探索后计划"是 fst-change
  内部方法，不是第 5 个模式）——否则文档表格、技能关联、README badge 三处各自为政
- 迁移权威位置时，全仓 grep 所有引用（**含 gitignore 的实例目录**，搜索工具会跳过，
  需逐个文件手动处理）同步更新

## 纪律 6：骨架复用与裁剪

多技能插件共享一个骨架契约（`references/skill-structure.md` 声明 `##` 标题），
`tools/verify/verify.mjs` 的 repeated-guidance 探针据此把重复标题识别为结构而非重复指导：

- 流程技能：完整 10 节骨架（职责 / Iron Law / Red Flags / 停止条件 / 执行流程 /
  用户 vs Agent / 关联最佳实践 / 输出 / 自检 / 下一步）
- 入口技能 / 内部路由技能：**允许裁剪**（如 router 无 Red Flags / 自检清单）
- 骨架是"结构声明"不是"内容复制"——每技能只填独有内容

## 纪律 7：维护纪律（引用一致性）

改一处权威，必须同步全链路，否则下次 verify 或使用者会踩到过期引用：

1. 改权威源（技能 / 参考文档 / 模式定义）
2. `grep -rn <旧名>` 全仓扫引用（含 gitignore 目录、CLAUDE.md、README、模板）
3. 更新所有引用为权威新位置
4. 校验三连：骨架完整性（frontmatter + 章节）→ 残留引用 = 0 → schema 测试全过
5. 双向引用抽查：主技能引用内部技能、内部技能被主技能/入口引用

## 自查清单（设计生成插件时逐条过）

- [ ] 规划/执行/横切/决策四个"谁做"已分开，各写进 Iron Law
- [ ] 需要选择+确认的逻辑已抽内部路由技能（结构化交接产物）
- [ ] 入口场景表覆盖 7 类场景，含简单任务与"拿不准"回退
- [ ] 框架与模式分两个权威位置，且随插件分发（非工作区模板）
- [ ] 模式集定版，无旧名残留；非独立概念已降级为内部方法
- [ ] 技能骨架共享声明 + 内部技能裁剪合理
- [ ] 全仓引用已同步（含 gitignore 目录），残留 = 0
