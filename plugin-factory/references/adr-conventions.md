# ADR 约定（Architecture Decision Records）

> **固化于：2026-08-02** · 对齐 Martin Fowler《Architecture Decision Record》与社区共识。
> **规则**：本仓库与生成插件的架构决策记录遵循本文——不要重复搜网。
> 冲突时以本文为准，并同步修正本仓库已接受的 ADR。

## 为什么存在

ADR 记录**一个决策**：系统为什么长成这样、考虑过哪些备选、代价是什么。
代码展示"是什么"，ADR 保存"为什么"——后者是最昂贵、也最容易丢失的知识。
写 ADR 本身也是澄清思考的过程：把决策写下来会暴露分歧，逼团队讨论并收敛。

## 何时写（触发标准）

只写**重大、难逆转、约束未来**的决策：

- **难逆转**：改造成本高、推翻代价大；
- **影响多个组件 / 多端 / 多人**：波及面超出单个技能或单端；
- **约束未来选择**：一旦做了就限制后续路线。

判定测试：**一位新高级工程师不知道这个决策会不会被坑？** 会 → 写；不会 → 不写。

**绝不**为每个小决策写 ADR——过度文档化是 ADR 实践崩溃的头号原因。
本地、可逆转、可随时改的决策直接做，不进 ADR。

## 状态机（不可变链）

每个 ADR 有且仅有一个状态：

| 状态 | 含义 |
|------|------|
| `Proposed`（提议中） | 讨论中，未接受 |
| `Accepted`（已接受） | 团队接受并生效 |
| `Superseded`（被取代） | 决策已变更，链接到取代它的新 ADR |
| `Deprecated`（弃用） | 不再适用且无直接替代（显式废弃） |

**不可变性铁律：已接受的 ADR 永不编辑。** 决策变更时写一篇新 ADR，把旧 ADR
标记为 `Superseded by ADR-NNNN` 并互相链接。编辑历史 = 抹掉 ADR 存在的意义——
决策演进的链条正是 ADR 的全部价值。

## 存放与格式

- 存放于 `docs/ADR-NNNN-<kebab-case>.md`（仓库内、与代码同处一库，可 diff）。
- 每篇一页（单屏），Markdown，编号单调递增，文件名捕获决策主题。
- **倒金字塔**写作：最重要的放最前，细节靠后。
- 内容段（模板）：

```markdown
# ADR-NNNN — <决策标题>

- **状态**: Accepted | Proposed | Superseded | Deprecated
- **日期**: YYYY-MM-DD
- **背景（forces）**: 为什么需要这个决策；驱动的约束。

## 决策

一句话 + 必要细节。

## 理由

关键权衡；**明确列出所有认真考虑过的备选方案及其被否决的原因**
（这是终止未来争论、向后来者解释选择的关键）。

## 后果

变得更容易 / 更难的事；触发重访的上下文变化（什么变了就该重新评估）。
```

## 流程

1. 重大决策即将落地时写 `Proposed` ADR。
2. 经讨论 / 评审后接受（走 PR 评审，同 PR 内落地决策实现）。
3. 已定决策被重新辩论时——优先指向已有 ADR；没有 → 这就是补写信号的提示。
4. 决策变更 → 新 ADR `Accepted`，旧 ADR 标记 `Superseded` 并链接。

## 补写（Retroactive）

团队最常被新人问"为什么这么做"的已落地决策，可以 retroactively 补写一篇
`Accepted` ADR——花十分钟，立即证明价值并开启日志，胜过空谈流程。

## 验证

`scripts/verify.mjs` 的 `adr-status` 探针检查：编号连续、状态字段合法、
`Superseded` 链接存在（INFO/WARN 级，不阻断门禁）。
