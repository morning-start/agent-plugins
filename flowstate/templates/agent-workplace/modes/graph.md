# Graph 模式（流程框架：Agent 执行图）

> 定位：**Graph 不是解决单一问题的最佳实践，而是整套流程的执行框架**。
> 它与 modes/ 里的 plan/spec/task/goal 是两层东西——框架（骨架）vs 实践（工具）。
> 本文件定义工作区如何承载 flowstate 的执行图（见项目 `docs/PRD.md` §七）。

## 两层架构（先看清自己在哪一层）

| 层 | 是什么 | 变化频率 | 本工作区位置 |
|----|--------|---------|-------------|
| **流程框架（Graph）** | 整套开发流程的结构：节点、边、循环、闸门 | 慢——符合现代开发哲学与现实条件，不随单一问题变化 | 本文件 + `state/` |
| **最佳实践库（modes/）** | 解决单一问题的方法：Plan / Spec（方略）/ Loop / Graph（方略）等 | 快——随经验不断更新、可插拔 | `modes/*.md` |

**关系**：流程的**每个节点**可以选用不同最佳实践去执行——
例如 N4（迭代开发）可用 Spec/Loop/Graph 方略，N1（立项）可用 Spec 模式的访谈环节。
框架定"流程怎么走"，实践定"这一步怎么做得更好"；两者解耦，互不绑架。

## 执行图结构（工作区视角）

```
节点（Node）   = 流程环节：F1~F9 → N1~N9
边（Edge）     = 流转条件：DoD 核销是边上的守卫（guard）
条件边         = 变更分级路由（轻微/中度→回开发，重大→回设计）
循环（Loop）   = 变更回环（N4→N5→N4）、迭代闭环（N8→N4）
人工闸门(HITL) = 必须暂停等人确认：底线冻结/范围签署/分级确认/重大审批/放量决策/DoD 核销
检查点(Checkpoint) = 断点续跑：`state/checkpoint.json`
并行（Parallel）   = 多变更单并行评估（`state/artifacts.json` 注册）
短路（Shortcut）   = Hotfix 直通车：任意节点 → N9 → N6
```

## 工作区如何承载图

| 图元素 | 落地位置 | 说明 |
|--------|---------|------|
| 当前节点/phase/batch | `state/checkpoint.json` | 每批完成即更新，断点续跑 |
| 目标与自我评估 | `state/goal.md` | Goal 模式与图的迭代闭环协同 |
| 产物注册 | `state/artifacts.json` | 跨节点追踪产出物 |
| 过程文档 | `docs/` | 各节点的产出物（plan/task/spec/requirements/decisions） |
| 实验验证 | `scripts/` + `scratch/` | 节点的"怎么做才对"验证 |

## 铁律（图执行约束）

1. **未核销不能沿边前进**：DoD 未核销，不得进入下一节点（见 `docs/PRD.md` §7.2）
2. **闸门必须等人**：HITL 节点强制暂停，AI 不得越权代做"只允许人做"的决策
3. **变更必须走边**：任何新需求/改动先进 N5（变更管控），记录原文、分级、评估后才动代码
4. **断点必存**：每节点/每批完成写 `state/checkpoint.json`，中断可恢复
5. **骨架必过冒烟**：未确认需求只做骨架，但骨架必须通过冒烟测试

## 与单点最佳实践的关系（解耦要点）

- 选择实践**不改变框架**：换一种最佳实践只是换"这一步的解法"，图的节点/边不变
- 更新实践**不推翻流程**：modes/ 里加新实践（如新出的 TDD 模式）不影响流程骨架
- 框架演进**缓慢且受控**：改流程结构需走项目 ADR（如 `docs/ADR-0002-agent-graph.md`），
  不是随手调整

## Graph 方略（phase→graph / phase→task→graph）

> 上面的内容是**流程框架**（N1~N9 全局执行图）；本节是**图方略**——把图编排
> 思想下放到迭代内部，作为 fst-iterate 的第三种方略使用。

### 定位（两种粒度）

| 粒度 | 链条 | 用法 |
|------|------|------|
| phase 级 | `phase→graph` | 一个 phase 内各任务按依赖图编排：节点=任务、边=DoD/依赖，拓扑推进 |
| task 级 | `phase→task→graph` | 单个任务内部拆子步骤，按子图执行（如重构步骤的依赖链） |

**何时选它**：任务间依赖复杂、可并行、需要按拓扑顺序推进时选 graph；
每步独立可验收时选 spec（见 `modes/spec.md`）。

### 流程

1. **建图**：把 phase/task 拆为节点（任务或子步骤），用 `deps` 字段标依赖边；
   每节点标注验收标准（与 spec 方略共用 `acceptance`）
2. **拓扑执行**：按依赖顺序推进——无前置依赖的节点先行；无相互依赖的节点可**并行**
3. **每节点核销**：节点完成 = 该节点验收标准核销（DoD 守卫），未核销不得进入下游节点
4. **条件边 / 回环**：执行中发现新变更 → 走 N5 变更管控（回环）；节点失败 →
   回退到依赖它的上游节点，不整体重跑
5. **断点续跑**：每节点完成写 `state/checkpoint.json`，中断可恢复

### 产物

`docs/task/TASKS.md`（`deps` 字段已支持）· `state/checkpoint.json`（拓扑进度）·
可选 `docs/task/graph.md`（图可视化：mermaid / 依赖列表）

### 与全局执行图（N1~N9）的关系

- N1~N9 图：**流程骨架**，定"整个开发怎么流转"（本文件上半部分）
- Graph 方略：**图内节点（如 N4）内部**的任务编排方式，不改变流程骨架
- 一条铁律不变：**无论用什么方略，DoD 未核销不得沿边前进**
