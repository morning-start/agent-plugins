# /fst-iterate — 迭代循环

启动 flowstate 迭代开发流程（N4 开发 / N8 持续迭代）。加载并遵循 `skills/fst-iterate/SKILL.md`。

## 步骤

**0. 盘点本轮需求 + 选方略（需求驱动，前置）**

- 盘点**本轮迭代要交付/要改动的那部分需求**（不是整个项目需求）：
  - 迭代范围说明书排期需求（REQ-xxx，fst-init 签署）
  - 已归档变更单（CR-xxx，fst-change）——**新需求、新改动就是这里**
  - 需求池中排入本轮的条目
- 产出**本轮需求清单**（新功能 / 需求改动 / 缺陷修复 / 技术债偿还 分类）
- 按需求特征选方略，向用户确认后再设计：
  - 常规开发、验收点清晰 → `spec`（默认）：任务带验收标准，逐项核销
  - 目标明确但边界模糊、需反复逼近 → `loop`：目标循环（完成条件 → 每轮自评 → 达标停止）
  - 依赖复杂、跨模块、可并行 → `graph`：任务依赖图（deps 拓扑推进、可并行）
  - 一句话能说清 diff 的简单任务 → 不进方略，直接做（todo 轻量清单）

**1. 方略设计：写 docs/plan**（分 phase + 声明方略）：按大阶段拆分（基础层 → 核心流程 → 交互/外围 → 打磨/上线准备），每 phase 写清"要做什么 / 为什么做"，并声明执行方略（来自第 0 步选型）

**2. 方略设计：细化 docs/task**（分批 + 验收标准）：按内聚程度（同模块/同层）与实现顺序（先依赖后上层）分批；`spec` 方略下每个任务带 acceptance，完成 = 验收标准核销

**3. 按方略实现**（Git 分支开发，F4.2）：
- 一个功能/变更单 = 一个分支（`feat/CR-001`），修复走 `fix/<bugslug>`
- 一批一验（构建/冒烟），提交信息带变更单 id

**4. 批次验收 Gate**（每批必过）：Schema 验证（`npm test`）+ 构建 + 冒烟 + 自检清单

**5. 维护技术债清单**（schema 5.6）：登记妥协实现、原因、偿还迭代

**6. 迭代末回顾**（schema 5.7）：交付统计 / 变更统计 / 度量（完成率、返工率、需求池积压）/ 风险与技术债 / 下轮建议

**7. 下轮排期**：确认下轮迭代范围 → 回到第 0 步（N8→N4 持续迭代闭环）

## 规则

- 先盘点需求，再选方略，后设计，最后执行——不盘点直接开写 plan 属于跳过决策
- 每个 phase 必须声明方略（来自需求特征选型），任务必须可验证（验收标准核销 / 每轮自评 / 节点 DoD）
- 不写 plan/task 不动代码；任务不分批不实现（一批一验）
- 未确认需求只做骨架开发（骨架须过冒烟）
- 变更单未归档不得开新分支

## 下一步

迭代中变更 → `/fst-change`；验收 → `/fst-review`；回顾完成 + 下轮范围确定 → 回到本命令（闭环）。
