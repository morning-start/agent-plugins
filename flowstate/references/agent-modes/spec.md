# Spec 模式（验收驱动）

> 定位：把工作拆成带**可验证验收标准（acceptance）**的任务，完成 = 验收标准逐项核销。
> 是「每步可验证」的默认 mode，适合验收点清晰的常规开发。

## 是什么（本质）

每个任务都带一条或多条**可验证的验收标准**（是可断言的判据，而非「实现 XX」这种模糊表述）。
任务「完成」的定义是：这些验收标准**逐项核销通过**——未核销不算完成；
无法客观验证的任务，要么拆细、要么补验证手段，绝不写「大概完成」。

## 何时选用

- 验收点清晰、每步可验证
- 常规功能开发、缺陷修复
- 是**默认优先**考虑的模式（最通用）

**反例**：边界模糊、需反复逼近 → 用 **Loop 模式**；依赖复杂、可并行 → 用 **Graph 模式**。

## Iron Law

```
NO ACCEPTANCE, NO COMPLETE
```

- 每个任务必须带**可验证的验收标准**，不能只有「实现 XX」
- 验收标准是断言（「接口返回 200 且字段 Y 非空」「冒烟通过」「Schema 校验通过」）
- 无法客观验证 → 拆细、补验证手段，或标「待确认」，不写「大概完成」

## 执行步骤

1. **写任务清单**：编号 + 标题 + 描述 + **验收标准（acceptance）**
2. **分批**：按内聚（同模块/同层）与实现顺序（先依赖后上层）分组
3. **逐批执行 + 逐项核销**：每批完成后对照验收标准逐项验证（构建 / 冒烟 / 测试 / Schema 校验）
4. **处理未核销项**：记录为技术债或阻塞，**不标「已完成」**
5. **（可选）汇总验收清单**：跨任务汇总验收项，供最终 DoD 核销直接引用

## 产物

- **任务清单**：每个任务含 `acceptance`（验收标准）字段
- 可选：**验收清单**（跨任务汇总的验收项，供终验引用）

## 与其他模式的关系

- 与 **Todo**：todo 是「不用想就能做」的简单任务；spec 是需要「逐项验收」的正式任务
- 与 **Goal**：spec 每步可验收（边界清晰）；goal 目标循环（边界模糊、需逼近）
- 与 **Graph**：spec 定义「每个节点做到什么算完成」，graph 定义「节点之间怎么走」
