# Spec 模式（验收驱动）

> **一句话**：把工作拆成带**可验证验收标准**的任务，完成 = 验收标准逐项核销。
> 是四种 mode 中的**默认执行模式**，适合验收点清晰的常规开发。

## 职责边界

| | 说明 |
|---|---|
| **负责** | 把工作拆成带可验证验收标准的任务（描述 + 验收标准 + 验证步骤 + 依赖）；逐批执行并逐项核销验收标准判定完成；汇总验收清单供终验 |
| **不负责** | 需求访谈澄清（立项阶段 `fst-init` 的职责）、依赖图编排（Graph）、边界模糊的长跑逼近（Loop）、一句话 diff 的直做（Todo） |
| **何时转交** | 任务验收点模糊需反复逼近 → 转 **Loop**；多依赖可并行 → 转 **Graph**；单点小改 → 转 **Todo** |

## 触发

**触发（Use when）**——默认优先，满足任一：

- 验收点清晰、每步可验证
- 常规功能开发、缺陷修复
- 从立项（`fst-init`）产出的任务清单进入执行
- 工作可拆成多个带验收标准的任务，且任务间依赖简单（复杂依赖见 Graph）

**明确不触发（Do NOT use when）**——满足任一即退出：

- 边界模糊、需反复逼近 → 转 **Loop**
- 依赖复杂、可并行、需显式先后 → 转 **Graph**
- 一句话能说清 diff → 转 **Todo**（不必走完整验收流程）

## Iron Law

```
NO ACCEPTANCE, NO COMPLETE
```

- 每个任务必须带**可验证的验收标准**，不能只有「实现 XX」
- 验收标准是**断言**（「接口返回 200 且字段 Y 非空」「冒烟通过」「Schema 校验通过」），不是描述
- 无法客观验证 → 拆细、补验证手段，或标「待确认」，不写「大概完成」
- **证据门**：声称任务「核销」前必须有**本消息内刚跑过**的验证输出；未跑过验证 = 未核销

## 流程

> 门控：每批完成后**暂停**，对照验收标准逐项核销；未核销不得进入下一批。

1. **写任务清单**：每个任务含——
   - **编号 + 标题**：一句话，不含"和"（含"和"说明是两个任务）
   - **描述**：一段话说明该任务完成什么
   - **验收标准（acceptance）**：3 条以内可勾选的断言（可测试条件）
   - **验证步骤（verification）**：跑什么命令 / 做什么检查来证明验收标准（如 `npm test`、`build`、冒烟）
   - **依赖（deps）**：前置任务编号，或「无」
2. **分批**：按内聚（同模块/同层）与实现顺序（先依赖后上层）分组；每批可独立验证
3. **逐批执行 + 逐项核销（证据门）**：每批完成后跑验证步骤，**读到输出**确认每项验收标准通过，才核销进下一批
4. **处理未核销项**：记录为技术债或阻塞，**不标「已完成」**；修复后重新跑验证再核销
5. **（可选）汇总验收清单**：跨任务汇总验收项，供最终 DoD 核销直接引用

## 产物

- **任务清单**：每个任务含 `acceptance`（验收标准）+ `verification`（验证步骤）+ `deps`（依赖）字段
- 可选：**验收清单**（跨任务汇总的验收项，供终验引用）

## 自我怀疑（Rationalizations to Reject）

| 借口 | 现实 |
|------|------|
| "这任务很简单，不用写验收标准" | 简单任务可以写短，但不能没有；验收标准是完成的唯一判据 |
| "验收标准太难写，先做着看" | 写不出来说明理解不够 → 拆细、补验证手段或转 Loop |
| "先写代码，验收标准回头补" | 那是文档不是规格；验收标准的价值在实现**之前**强制澄清 |
| "任务太模糊，将就写个验收" | 模糊的验收 = 无验收 → 转 Loop（边界模糊就逼近）或先澄清需求 |
| "测试跑过就行，不用写验证步骤" | 验证步骤 = 验收标准的**证据来源**；不写明就无法证明核销 |
| "应该没问题，不用重跑" | 证据门要求本消息内刚跑过；旧结果不构成核销证据 |

## 红旗（Red Flags - STOP）

- 出现无验收标准的任务 → 停，补验收标准
- 验收标准是描述（"实现 XX"）而非断言 → 停，改成可测试条件
- 打算用「大概完成」收尾 → 停，先核销或转 Loop
- 任务验收点反复变、无法客观验证 → 停，重新澄清或转 Loop
- 声称核销但本消息内没跑过验证 → 停，跑验证再看输出

## 验证（Verification）

- [ ] 每个任务都有可验证的验收标准（断言式，非描述式）
- [ ] 每个任务都有验证步骤（命令 / 检查，证明验收标准）
- [ ] 任务依赖已标注（`deps`），分批可独立验证
- [ ] 所有验收标准已逐项核销通过（本消息内有验证输出）
- [ ] 未核销项已明确记录（技术债 / 阻塞），未标「已完成」
- [ ] 汇总验收清单已产出（如适用）

## 与其他模式的关系

- **→ Loop**：验收点模糊、需反复逼近 → 升级
- **→ Graph**：多依赖、可并行、需显式先后 → 升级
- **→ Todo**：单点小改、一句话能说清 diff → 降级
- **← fst-init**：立项产出任务清单后，由 Spec 模式承接执行
- 与 **Graph**：spec 定义「每个节点做到什么算完成」，graph 定义「节点之间怎么走」——graph 的节点常用 spec 的验收方式核销
