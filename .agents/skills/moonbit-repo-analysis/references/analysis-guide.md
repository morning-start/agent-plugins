# 分析哲学与思维框架（吸收自 repo-analyzer）

## 核心立场

分析的目标是让读者**学到东西、产生思考**，而不是获得一份代码说明书。好的分析像一位资深工程师在白板前讲解——有观点、有推理、有对比，读完后读者能参与架构讨论。

每个评价都需要：代码依据、对比基准、推理过程。

## 从项目特征中发现值得深挖的点

**追问设计动机**：看到一个设计选择时，问"为什么不用更常见的方案？"如果答案没有特别原因，这可能是一个改进点；如果答案揭示了深层约束，这就是值得展开的洞察。

**寻找张力点**：好的架构是在矛盾需求之间找平衡——性能 vs 可读性、灵活性 vs 简单性。这些张力点往往是最有分析价值的地方。

**识别设计哲学**：大多数成熟项目有贯穿始终的设计风格（"约定优于配置"、"零成本抽象"）。识别这个哲学，然后检验它是否被一致地贯彻。

**关注边界**：模块边界、抽象层边界——边界的设计往往比内部实现更能体现架构思考。一个模块内部可以随时重写，但边界一旦确定就很难改。

## MoonBit 特有的分析角度

### WASM 优先的设计约束
MoonBit 项目通常以 WASM 为首要目标。这带来独特的分析维度：
- 为什么选择 WASM-only vs 多平台？（性能优势 vs 生态限制）
- WASIp1 的约束如何影响错误处理（无 panic/stacktrace，stderr 是唯一信道）
- 预打开目录（preopen）如何影响路径设计和 API 抽象

### 类型系统利用程度
MoonBit 的类型系统介于 Rust 和 Go 之间。分析时关注：
- 是否使用了 `trait` 和泛型？是保守使用还是深度依赖？
- 错误处理用 `raise`（异常风格）还是 `Result`？为什么？
- `pub(open)` 和 `#internal` 标记如何控制封装边界

### 与 MoonBit 生态的集成
- 是否依赖 mooncakes 上的第三方包？依赖管理是否合理？
- 库是否附带 `skills/` 或 AGENTS.md 供 AI Agent 使用？
- CI 是否同时覆盖 Windows/Linux/macOS 和 WASI 运行时？

## 如何写出有启发性的分析

### 对比式思考
每个设计决策都存在于一个选择空间中。好的分析不只描述"选了什么"，还要说明"没选什么以及为什么"。

### 反事实推理
"如果不这样做会怎样"是检验设计必要性的利器。如果去掉一个设计元素后系统仍然正常工作，那它可能是过度设计。

### 设计权衡三角
大多数架构决策涉及三个维度的权衡：
- 简单性 / 灵活性 / 性能
- 开发速度 / 运行时安全 / 学习曲线

## 全局关联

每个局部分析都必须连接到项目整体设计哲学。这是区分"代码说明书"和"架构分析"的关键：
- 分析一个模块时，先说明它在整个系统中扮演什么角色
- 解释一个设计决策时，说明它如何服务于项目的整体设计哲学
- 描述模块间协作时，解释这种协作模式是否与项目其他部分一致

## 叙事连贯

模块分析不是独立章节的拼接，而是一条有逻辑的叙事线。

常见的叙事主线：
- **数据流驱动**：跟随请求/数据从入口到输出的路径
- **分层驱动**：从底层 FFI 讲到上层公共 API
- **问题驱动**：从核心问题出发，逐步引入解决每个子问题的模块

过渡句示例：
> ✅ Gateway 完成了请求的认证和路由分发，但它只负责"谁可以进来"，不负责"进来之后能做什么"。
> ❌ 接下来我们分析策略引擎模块。

## 深度标准

有深度的分析特征：具体的技术推理、量化的权衡、业界对比、"为什么适合这个项目"的判断。

没有深度的分析特征：泛泛而谈、没有具体技术细节、没有推理过程、换一个项目也能用。

## MoonBit 专题：如何分析 Skill 设计

当项目包含 `skills/` 目录时，额外分析：
- SKILL.md 的 description 字段是否支持 Agent 语义路由
- 模板（assets/）是否足够减少 Agent 输出变异性
- 验证管线是否与技能生命周期匹配（长期技能 → 完整构建链，一次性技能 → 命令即验证）
- 技能之间是否有编排关系或依赖声明
- 是否包含错误恢复协议和前置检查门（7 维度工程化标准）

参考 `references/report-structure.md` 的章节 4（Skill & 编排分析）。
